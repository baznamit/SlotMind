The scenario
CareBridge clinics schedule patient appointments with providers across multiple rooms. When a provider calls in sick or a room becomes unavailable, a front-desk coordinator manually calls patients, checks who can be moved, and rebooks. Patients wait on hold, slots go unused, and double-bookings happen when two coordinators work the same list.

Today, someone notices the cancellation and fixes it by hand. It works — but it's slow, depends on who's at the desk, and fails silently when the clinic is busy.

That's the problem you're solving. When a provider goes offline or a slot is cancelled, your system identifies affected appointments, uses AI to recommend rebook options, and queues those recommendations for front-desk approval — without anyone clicking a button.
Scope for this sprint
You're building a reactive re-scheduling engine — not a full practice management system. Patient portals, billing, and waitlist auto-fill are sprint 2 and 3. Nail the re-schedule loop and build foundations for those extensions.
What you're building
  • A domain model — Appointment, Provider, Slot, RescheduleSuggestion with explicit state machines
  • A scheduling engine — pluggable strategy interface: rule-based (nearest open slot, same provider preference) and AI-powered
  • An AI scheduling advisor — recommended slot, alternate provider if needed, confidence, patient-friendly explanation staff can read aloud
  • An agentic re-schedule loop — provider OFFLINE or slot CANCELLED triggers async suggestions for all affected appointments
  • A front-desk UI — affected appointments, AI reasoning, accept/reject, badge for auto vs manual triggers
A few things worth knowing
  • Solo effort — every architectural call is yours.
  • AI tools encouraged. Understand what you ship; we'll walk through it together.
  • Walkthrough traces: book appointment → provider goes offline → suggestion appears → accept updates slot atomically.
  • Submit: public GitHub repo, 5-minute demo, ADR.md.
  • Addenda provide seed data and LLM gateway boilerplate.
T-1
Domain model & API
Backend20 pts~50 min
Appointment — patient name, type (ROUTINE, URGENT, FOLLOW_UP), provider, slot, lifecycle: CONFIRMED → RESCHEDULE_PENDING → RESCHEDULED → COMPLETED

Provider — name, specialty (GENERAL, SPECIALIST, PEDIATRIC), status: AVAILABLE, BUSY, OFFLINE

Slot — start time, duration minutes, linked provider, status: OPEN, BOOKED, CANCELLED

RescheduleSuggestion — appointment reference, recommended slot ID, optional alternate provider, confidence, reasoning (patient-friendly), status (PENDING → ACCEPTED | REJECTED), triggerReason (INITIAL, PROVIDER_OFFLINE, SLOT_CANCELLED)

Endpoints:
  • POST /appointments — book to provider + slot
  • GET /appointments?status= — filterable list
  • PATCH /providers/{id}/status — OFFLINE fires agentic loop
  • PATCH /slots/{id}/status — CANCELLED fires agentic loop
  • POST /appointments/{id}/suggest — on-demand reschedule
  • PATCH /suggestions/{id} — accept or reject
Transactional accept
Accepting a suggestion must update appointment + old slot + new slot atomically. No double-booking.
T-2
Pluggable scheduling engine
Backend · Design Pattern25 pts~55 min
Contract: given appointment + available slots/providers, return ordered recommendations.

Rule-based strategy — prefer same provider's nearest open slot; if none, nearest open slot with matching specialty.

AI strategy — T-3; design interface with appointment urgency and patient context in mind.

Runtime switchable via config. Both HTTP and async loop callers use same contract.
Sprint 2 heads up
RoomConstraintStrategy should mean implementing the contract and registering — nothing more.
T-3
AI scheduling strategy
AI Integration25 pts~55 min
Give the LLM: appointment details, urgency, available slots with times, provider roster, trigger context (provider offline vs slot cancelled).

Expect: slotId, optional alternateProviderId, confidence, reasoning suitable for staff to read to patients.

  • Validate slot ID and provider ID against actual data
  • Ensure recommended slot is actually OPEN
  • Fallback to rule-based on LLM failure
Two prompts
Provider offline vs slot cancelled are different recovery situations. Offline may require alternate provider; cancelled may only need a new slot with same provider.
Bonus · +5 pts
POST /appointments/{id}/suggest/stream — SSE reasoning stream.
T-4
Agentic re-schedule loop
Agentic15 pts~45 min
On provider OFFLINE: find all CONFIRMED appointments for that provider, run scheduling engine, create suggestions with triggerReason = PROVIDER_OFFLINE.

On slot CANCELLED: find appointment on that slot, run engine, create suggestion with triggerReason = SLOT_CANCELLED.

  • Endpoints return immediately — re-scheduling is async
  • Skip duplicate PENDING suggestions for same appointment + triggerReason
  • AI failure → rule-based fallback, not silent drop
Human checkpoint
System proposes new slot; front desk confirms with patient before accept finalizes booking.

T-6
ADR + live walkthrough
Architecture ownership20 pts
Cover: scheduling logic placement, strategy switchability, transactional accept design, agentic loop decoupling, extensibility (room constraints in sprint 2).
ADR format: Context → Options → Decision → Tradeoffs.
1 Where does scheduling logic live?
Service vs domain. How do you prevent booking conflicts at the domain boundary?
2 Runtime strategy switching
Bean map, factory, or registry — works from HTTP and async paths.
3 Transactional accept
How accept updates appointment, frees old slot, books new slot in one transaction. Optimistic locking or DB constraints?
4 Agentic loop decoupling
Two trigger types (provider offline, slot cancelled) through same or separate event handlers?
5 Extensibility and exclusions
Where room/equipment constraints plug in. What you deferred.
Sprint 2 — Constraints & Preferences
  • Room and equipment requirements per appointment type
  • RoomConstraintStrategy as third scheduling option
  • Patient preference history — morning vs afternoon
  • Appointment duration varies by type
  • Provider max daily appointments
Sprint 3 — Waitlist & Notifications
  • Waitlist auto-fill when slot opens
  • SMS/email on accept
  • Multi-clinic routing
  • AI considers downstream provider queue pressure
  • Patient self-service reschedule portal
AGT-1 Two triggers, one loop?
Provider offline affects many appointments; slot cancelled affects one. Same handler with branching or separate events?
AGT-2 Patient-friendly AI output
Reasoning should be suitable for staff to read to patients — not internal jargon.
AGT-3 No double-booking on accept
Race condition if two staff accept suggestions for the same slot. How does your design prevent it?
